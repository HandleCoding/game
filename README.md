# 一起玩 · 好友游戏大厅

独立部署在京东云，入口 https://game.aicoding.ltd 。大厅支持多个账号同时在线，每个游戏单独开房。当前游戏：**猜数字（2 人）**。

## 游戏规则

双方准备 → 各自锁定 0000–9999 的四位数字（保留前导零，可重复）→ 掷骰子（平局重掷）→ 高点先猜 → 双方轮流猜。系统只返回相同位置命中数，4 位命中获胜。默认每回合 30 秒，房主可在开局前选择 15 / 30 / 45 / 60 / 90 秒；修改设置会取消双方准备状态。

默认显示历史猜测和对应命中数量，支持按自己的、对方的和全部查看。房主可开启“禁用历史 · 记忆模式”（默认关闭）：进行中只短暂提示刚提交的猜测及命中数量，界面不提供历史列表。输入框上方显示对方当前状态和最近一次提交的数字、命中数量，下一次提交后覆盖；进行中自己的历史及对方更早的猜测不向客户端发送。双方必须重新准备才能开始。

对局结束后，两种模式均开放双方完整猜测记录与每次命中数量，包括最后猜中答案的记录及超时跳过的回合。复盘默认展示全部记录，按回合从早到晚排列，也可筛选自己的或对方的猜测。刷新结算页面仍可查看，重新开局后清空本局记录。

没有加好友机制；所有在线玩家都出现在大厅，可以直接邀请空闲玩家。正在房间里的玩家显示具体游戏、等待 / 进行中 / 结束状态，进行中显示开局时长。

收到邀请显示弹窗，可接受或拒绝，15 秒未回应自动拒绝。邀请方实时收到接受 / 拒绝 / 超时提示。加入房间时会清除同房间的其他邀请，避免邀请过期后仍显示可加入。

超时跳过该回合。连接断开暂停计时，保留 60 秒重连机会。主动离开结束本局，另一方获胜。服务器保存账号、对局结果与当前房间；重启后玩家需要在 60 秒内重新连接。

## 当前运行方式与开发环境安排

开发和测试按用户要求放在京东云 `/opt/pair-play-dev`，使用独立进程和 `/var/lib/pair-play-dev` 数据目录，正式环境继续使用现有入口。Agent 从 [AGENTS.md](AGENTS.md) 和 [开发文档入口](docs/README.md) 接手。当前开发与正式均为 SQLite，后续迁移为一个 PostgreSQL 实例中的 `playroom_dev` 与 `playroom_prod` 两个独立数据库，详见 [技术选型与环境隔离](docs/technology-decisions.md)。以下命令说明原始代码的运行方式；在云端开发目录使用 [开发手册](docs/development-guide.md) 的独立服务或指定环境配置，不能无配置启动 3210 与正式服务冲突。

需要 Node.js 22.13+，无第三方依赖。

```sh
npm start
npm test
```

打开 http://127.0.0.1:3210 。数据默认在 `data/pair-play.sqlite`。可用 `HOST`、`PORT`、`DATA_DIR`、`PUBLIC_ORIGIN` 调整运行环境。生产环境务必设置真实 HTTPS `PUBLIC_ORIGIN`。

## 生产部署

- 代码：`/opt/pair-play`
- 数据：`/var/lib/pair-play/pair-play.sqlite`（包含账号、秘密数字等私有数据）
- 服务：`pair-play.service`，由独立低权限账号 `pairplay` 运行
- 监听：`127.0.0.1:3210`，Caddy 在 80 / 443 提供 HTTPS 与证书自动续期
- 配置：`/etc/caddy/Caddyfile`，原配置备份位于 `/etc/caddy/Caddyfile.before-pair-play-*`

```sh
systemctl status pair-play
journalctl -u pair-play -n 80 --no-pager
systemctl restart pair-play
curl http://127.0.0.1:3210/healthz
```

备份 SQLite 时应使用 SQLite 在线备份 API，或暂停服务后同时保存数据库及 WAL 文件；不要在运行中只复制 `.sqlite`。更新代码不应覆盖 `/var/lib/pair-play`。测试账号与测试数据库不能覆盖正式数据。

## 结构与扩展

浏览器（电脑 / 手机）→ Caddy HTTPS → Node.js 单进程 HTTP 服务 → SQLite。本项目使用 Node.js 原生 `http`、`crypto`、`node:sqlite`，无需 Express、Redis 或另一个数据库容器。浏览器通过 JSON HTTP 接口提交操作，通过 Server-Sent Events 接收实时状态；心跳维护连接，断线后自动重连。

SQLite 开启 WAL，保存 `users`（账号和密码哈希）、`sessions`（登录会话）、`results` / `result_players`（结算与玩家战绩）、`active_rooms`（当前房间快照）。在线连接与邀请在内存中；房间规则也在内存里计算，每次状态变化保存快照。房间快照便于重启恢复，但邀请不跨重启保留。

服务由 systemd 管理，开机启动、失败重启，使用独立低权限用户。只监听本机端口，对外由 Caddy 提供 HTTPS，证书由 Let's Encrypt 签发并自动续期。这是单机架构，适合目前的少量好友自用；若未来运行多个后端实例，需要把在线状态和对局协调放到共享存储。

`server.mjs` 管理账号、大厅、邀请、房间和 SSE 状态同步；`game.mjs` 管理猜数字规则；`public/` 为响应式网页。目前创建与恢复房间直接使用 `Duel`，人数、结算和前端仍有猜数字专属逻辑，尚未实现通用游戏模块接入。新增正式游戏前需要拆分注册表、房间机制与游戏界面，具体边界、接口、多人策略和兼容迁移见 [多游戏架构设计](docs/multi-game-architecture.md)。

目标架构分为对局型（打牌、下棋、猜数字）与长期型（农场、牧场、养成）。两类共用账号和大厅，长期存档、离线时间结算与互动事务独立于房间生命周期，具体设计见 [长期养成游戏架构](docs/persistent-game-architecture.md)。当前线上尚未接入长期游戏。

目标技术栈与迁移方案见 [技术选型](docs/technology-decisions.md)：Vue 3 + TypeScript + Vite 前端，Node.js + Fastify + TypeScript 后端，长期游戏正式启用前迁移至 PostgreSQL。上述是下一阶段的推荐方案，当前部署仍采用原生 JS / Node.js / SQLite。

服务器生成骰子、判断命中、校验操作和超时。客户端只收到自己的秘密数字，对方数字仅在结束后揭晓。密码采用随机盐与 scrypt，登录会话采用 HttpOnly / SameSite Cookie，HTTPS 下启用 Secure。

支持现代桌面与移动浏览器。手机端使用单栏布局、数字键盘和触控按钮，无需安装应用。移动浏览器进入后台可能中断连接，返回后通过 SSE 自动重连。

日间 / 夜间模式可通过顶部月亮 / 太阳按钮即时切换；首次跟随系统配色，手动选择保存到当前浏览器，同一浏览器的其他标签页同步主题。主题初始化在样式加载前完成。登录弹窗、房间、猜测记录、固定输入区与命中动画均支持两套配色，切换时不重建对局或清空草稿。

对局输入区固定在屏幕底部，查看历史时仍可输入；对方回合允许预写草稿，但只能在自己的回合提交。状态同步保留草稿、输入焦点与历史滚动位置。手机软键盘出现时根据 Visual Viewport 调整输入区位置。轮到自己时屏幕边缘淡绿色闪烁三次，之后保留淡色边框；断线或暂停时关闭提示。

掷骰显示滚动及落地动画，最终点数由服务器随机生成。命中 0 / 1 / 2 / 3 位分别使用灰 / 紫 / 蓝 / 金色提示，4 位全中显示揭晓与胜利彩屑。动画不影响服务器的规则判断；记忆模式的提示会移除，不形成隐藏历史列表。系统开启“减少动态效果”时关闭动画。

猜测输入区在电脑和手机上固定可见，支持边查看历史边输入；对方回合可以提前输入草稿，只有轮到自己时才能提交。收到新回合时屏幕边缘淡绿色闪烁，系统设置为减少动态效果时只保留静态边框。切换历史筛选或收到状态更新会保留草稿及记录滚动位置。
