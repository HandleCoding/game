# 长期养成游戏：农场与牧场架构

## 两种生命周期，共用一个大厅

| 项目 | 对局型 `match` | 长期型 `persistent` |
| --- | --- | --- |
| 示例 | 猜数字、下棋、多人打牌 | 农场、牧场、角色养成 |
| 开始方式 | 加入房间、准备、开局 | 登录后进入自己的持续存档 |
| 在线要求 | 根据游戏要求等待其他参与者 | 可以独自游玩，离线期间按规则成长 |
| 结束方式 | 胜负或退出，保存结果与复盘 | 一次操作结束，但整个存档持续存在 |
| 主要状态 | 房间、回合、牌局、棋盘 | 等级、货币、仓库、地块、动物与成长时间 |
| 再次进入 | 加入或重开一局 | 继续原进度 |

账号、会话、玩家目录、在线状态、主题、手机适配、动作认证与数据库连接共用。游戏注册表增加 `kind`，大厅根据游戏类型显示“创建房间 / 加入”或“进入游戏 / 继续游玩”。个人养成游戏不显示双人准备按钮，也不强制填写人数或每回合时间。

每个注册账号都可以拥有自己的农场、牧场档案；首次进入时在事务中创建初始档案，唯一约束保证同时用手机和电脑进入不会创建两份。不同游戏的货币、仓库与等级默认分开；以后如果农场和牧场共享经济，需要显式定义共同的世界与货币规则。

一个用户只限制同时参加一个对局房间。长期存档始终存在，玩下棋或退出农场界面不重置种植进度。多个浏览器或设备操作同一存档时，服务器负责一致性。

## 时间成长与离线结算

服务器保存行为发生时间和下次关键时间，而非依赖浏览器持续运行。

例如：10:00 种植，生长时长为 2 小时，记录 `plantedAt=10:00`、`readyAt=12:00` 和本次种植的规则版本。玩家 13:00 再进入时，服务器按真实时间得出“已成熟”，客户端只展示服务器确认的状态。

普通成熟判断可以在读取或操作时按时间计算；未登录的每个农场无需每秒改一次数据库。需要写入存档的离线生产则按上次结算时间、产出周期、仓库容量和饲料等条件计算，并在事务中更新结算游标，防止重复产出。

动物是否持续产出、是否需要喂养、作物是否会枯萎、离线收益上限，都属于对应游戏规则。要用明确的时间段与资源消耗计算，不能直接按离线小时数无限增加物品。服务器时间为准，修改手机时间不能提前收获；返回 `serverNow/readyAt` 供界面倒计时。

已种下作物或已开始的养殖周期保存适用版本和关键参数。之后调整新品种生长时间，不应意外修改正在生长的旧实例。

## 长期存档与数据库边界

当前线上使用 SQLite，结合多游戏和长期养成目标，推荐在首个正式长期游戏接入前统一迁移至 PostgreSQL，具体原因与迁移步骤见 [技术选型](technology-decisions.md)。使用有约束的结构化表管理货币、物品和可互动资源，游戏特有的非关键展示数据可用版本化 JSON。

建议按 `(game_id, world_id, user_id)` 区分档案；初期只有一个默认 world，提前保留世界标识避免以后合服或新增世界时混淆。所有子表外键带上对应档案范围。

- `persistent_profiles`：等级、经验、存档版本、revision、上次结算时间。
- `game_wallets`：游戏内各货币余额及约束。
- `game_inventory`：物品种类、数量；同一物品只有一条余额记录。
- `farm_plots`：地块、作物、种植时间、成熟时间、收获状态与规则版本。
- `ranch_animals`：动物实例、生命周期、喂养资源、产出游标与状态。
- `game_action_receipts`：请求编号、操作者、结果，用于动作去重。
- `game_ledger`：货币和物品变化及对应操作，方便追查异常。
- `world_jobs`：确需后台执行的事件、到期时间、状态与唯一事件键。

这些数据独立于 `active_rooms`。房间销毁、对局重开、玩家退出或 SSE 断开，都不能删除长期档案。存档使用独立版本迁移，备份包含数据库及相应一致性数据。

## 动作事务与跨玩家互动

游戏动作仍由服务器判断，不接受客户端提交最终余额、经验或成熟状态。

```text
GET  /api/games/:gameId/me
GET  /api/games/:gameId/players/:ownerId
POST /api/games/:gameId/actions
{ requestId, expectedRevision, type, payload }
```

登录会话决定操作者；访问别人农场时，目标 ownerId 与当前操作者明确区分。读取和动作先按需要完成时间结算，再验证状态，最终返回该操作者有权看到的结果。

一次“收获”在同一数据库事务中完成：确认地块成熟且未收获 → 标记消耗该收获机会 → 增加仓库物品 → 写入流水与去重结果 → 提交。购买、出售、喂养和跨玩家互动同样完整提交或完整回滚。事务期间不等待外部网络操作。

重复点击或网络重试使用 requestId 返回原结果，不重复增加金币或物品。手机与电脑同时收同一块地，或两名玩家同时操作同一资源时，利用条件更新、唯一约束和 revision 保证只结算一次；界面收到冲突后刷新目标状态。

所有注册玩家的可公开农场可以进入访问目录，无需添加好友。默认允许哪些参观、帮忙或其他互动，等具体玩法确定后单独定义；允许参观不能自动授权修改别人的存档。若设计偷菜、交易或赠送，必须明确资源上限、主人保留量、重复领取规则及双方事务，不直接复用房间邀请权限。

个人档案视图与访客视图分别生成。对外仅显示允许公开的地块、动物和互动机会；账户信息、完整仓库、货币与私人流水不默认公开。

## 在线状态与同步

大厅区分“正在进行一局游戏”和“正在浏览长期游戏”。短局保留“正在下棋 · 开局 X 分钟”；长期游戏显示“正在农场 / 牧场”，不会把已经存在几个月的存档当作持续了几个月的对局。

玩家进入农场时仍可收到短局邀请；接受后可以切换到对局，农场成长继续。后续如果需要一起参观，可以增加访问邀请，邀请类型与加入对局区分清楚。

SSE 在玩家在线时推送已提交的存档变化和访问目标的可见变化。离线期间保存数据库状态，重新连接后重新读取和结算即可。客户端倒计时只用于展示，倒计时归零不能直接入账。

## 后台事件与重启

必须在到期时执行的事件写入 `world_jobs`，例如季节变更或有规则要求的自动结算。后台定时扫描持久化任务并按唯一事件键执行；任务与资源变化在同一事务中确认完成，重启后继续处理逾期任务。

普通作物成熟不必为每秒创建任务；若成熟后还有枯萎等阶段，保存相应时间并在结算时按规则推进。系统重启后的补算必须覆盖多个已经发生的阶段，并遵守产能、饲料和容量上限。

对局型的“断线暂停 60 秒”仅属于相关对局政策。长期养成在断网、退出页面和服务器正常重启后，按保存时间继续推进，而不是暂停所有作物成长。

## 模块接口与接入顺序

长期模块与对局模块共享注册元数据，但使用自己的服务接口：

```text
ensureProfile(userId, worldId)       首次初始化
settleTime(profile, now, tx)        规则需要的离线结算
handleAction(actor, action, tx)     验证、操作和去重
viewFor(actor, ownerId)             私人或访客视图
migrateProfile(oldVersion, tx)      持续存档迁移
runJob(job, now, tx)                可选的持久化事件
```

先建立共同注册表与平台边界，再实现长期档案服务、时间结算与动作事务。农场和牧场可以先选择一个实现完整种养、收获、仓库和升级循环，再扩充访问互动。

验收需要覆盖：离线一天和跨重启后成长正确；同一地块并发收获只成功一次；重复请求不重复发货；出售和购买不出现负数或凭空增加物品；跨玩家操作遵守权限；访问视图不泄露私人数据；版本升级保留旧作物周期；手机与电脑使用同一份进度；正在下棋时农场仍正常成长。
