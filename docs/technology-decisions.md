更新：2026-10-04。背景：平台将包含短局牌类、棋类游戏，以及按账号持续保存的农场、牧场等养成游戏。PostgreSQL 已获用户认可；开发与测试也安排在京东云主机。本文是目标选型和部署设计，当前线上代码仍为原生 JavaScript + Node.js HTTP + SQLite，尚未进行框架或数据库迁移。

## 当前已经有后端

JavaScript 是语言，Node.js 是服务端运行环境。当前前端 `public/app.js` 在浏览器执行，后端 `server.mjs/game.mjs` 在京东云 Node.js 进程中执行。后端处理认证、规则判断、随机骰子、计时、数据库和 SSE，属于真正的服务器端程序。Node.js 的定位可见 [官方介绍](https://nodejs.org/learn/getting-started/introduction-to-nodejs)。

现在前后端同属一个项目，后端同时提供网页文件和 API，但客户端和服务端的运行位置及权限已经分开。未来需要进一步拆分源码、构建、接口与模块边界。

## 推荐选型

| 部分 | 目标选择 | 本项目中的用途 |
| --- | --- | --- |
| 前端 | Vue 3 + TypeScript + Vite | 大厅、独立游戏组件、响应式状态、移动端界面 |
| 后端 | Node.js 受支持的 LTS + Fastify + TypeScript | 统一认证、API、游戏注册、房间、长期档案 |
| 数据库 | PostgreSQL，接入首个正式长期游戏前完成迁移 | 账号、对局、长期进度、物品、货币、动作去重、任务 |
| 同步 | HTTP 操作 + SSE；按具体游戏需要增加 WebSocket | 当前猜数字及低频棋牌、养成状态同步 |
| 对外入口 | 现有 Caddy HTTPS | 同域静态文件与 API，现有域名、证书继续使用 |
| 组织方式 | 一个仓库、前后端独立构建、一个模块化 API 服务 | 共用基础能力，新增游戏有独立目录和契约 |

这是结合本项目需求的工程判断，而非框架本身保证容量或正确性。版本在实际迁移时选择受支持且兼容的稳定版本，提交锁文件并按测试更新。

### 前端选择理由

目前整个页面通过字符串与 `innerHTML` 重建，草稿、焦点和滚动需要手工恢复。随着牌桌、棋盘、仓库与地块组件增加，需要稳定的组件生命周期和状态更新边界。

Vue 3 + TypeScript 用于组织这些组件和约束界面接收的数据；Vite 用于开发和打包。Vue 官方提供 TypeScript 支持及基于 Vite 的脚手架：[Vue 中文文档](https://cn.vuejs.org/guide/typescript/overview)，[Vite 中文文档](https://cn.vite.dev/guide/)。

类型检查单独进入构建验收：`vue-tsc` 检查前端，`tsc` 检查后端与共享契约，不能以“Vite 打包成功”代替类型检查。TypeScript 类型也不能代替服务器运行时请求校验。

### 后端选择理由

Node.js 继续承担服务端运行。Fastify 提供路由、插件边界、请求校验和响应序列化，平台模块围绕这些能力组织；游戏引擎保持与 HTTP 框架无关。[插件隔离文档](https://fastify.dev/docs/latest/Reference/Encapsulation/)，[校验与序列化文档](https://fastify.dev/docs/latest/Reference/Validation-and-Serialization/)。

主要模块：accounts、sessions、lobby、invitations、matchRooms、persistentProfiles、gameRegistry、results、jobs。各游戏调用自己的规则模块，通用路由不持续添加该游戏专属分支。接口数据使用公共 schema，浏览器输入经服务器校验后才能进入规则。

先运行一个模块化后端。长期游戏确需后台处理时，让任务执行器调用相同的业务服务；任务持久化到数据库，执行器以后可以独立为 worker 进程。单个游戏只有在出现独立负载、故障隔离或技术环境需求时才单独部署。

### 数据库选择理由与迁移时间

SQLite 适用于当前好友自用的小规模单机程序，能够实现事务与养成游戏；不能将其表述为无法保存长期存档。但单个数据库文件同一时刻只有一个写入者，写密集或多服务场景适合评估服务器型数据库：[SQLite 官方适用场景](https://www.sqlite.org/whentouse.html)。

鉴于计划明确包含多个长期游戏、玩家之间的资源互动和经济数据，目标统一选 PostgreSQL，在农场或牧场的正式数据累积前迁移。这样初始就能围绕服务器型数据库设计并发事务、数据迁移、备份和任务执行。PostgreSQL 的并发控制见 [官方文档](https://www.postgresql.org/docs/current/mvcc.html)。

PostgreSQL 并不自动解决重复收获、负余额或多方争抢；条件更新、唯一约束、请求去重、正确的事务隔离和失败重试仍是业务代码责任。货币和数量使用合适的整数或精确数值类型。

一次受控迁移保留用户 ID、密码盐与哈希、结果关联、有效会话和房间快照。校验旧数据库与新数据库记录数量、关联和关键字段，验证原账号能够登录、活动房间能够恢复。切换时必须暂停写入或有明确同步方案，不能同时让两套数据库各自接受用户写入。

迁移前备份并演练恢复；迁移期间数据库版本与应用版本一同管理，明确回滚前是否已有新写入。新的养成数据只在新架构验收后正式启用。

## 京东云上的开发、测试与正式环境

用户指定开发、测试都在 `117.72.116.83` 京东云主机上运行，不要求 Windows 本机安装 PostgreSQL。浏览器可以在电脑或手机上访问服务器上的应用。2026-10-04 实机检查：4 核 CPU、约 16GB 内存，可用内存约 12GB，系统盘剩余约 59GB；足以作为当前规模两套环境的起点，后续按实际负载调整。

初期采用一个 PostgreSQL 实例、两个独立数据库，而非为每个游戏另建数据库实例：

| 环境 | 应用目录（目标） | 独立应用服务与端口 | 数据库（目标） |
| --- | --- | --- | --- |
| 正式 | `/opt/pair-play` | `pair-play.service`，`127.0.0.1:3210` | `playroom_prod` |
| 开发 / 测试 | `/opt/pair-play-dev` | `pair-play-dev.service`，`127.0.0.1:3211` | `playroom_dev` |

两个数据库使用不同的应用数据库账号和密码，分别配置连接字符串；取消不必要的公共连接权限，开发账号不具备访问正式库的权限。数据库结构迁移先在开发库演练，开发测试数据不直接覆盖正式存档。两个应用使用独立运行账号、环境配置、日志和私有数据目录；作业执行器跟随环境隔离，不能读取另一套环境的任务。

开发测试不停止或重启正式应用。代码在开发目录构建和验证，再发布经过验收的版本到正式目录，不能让正式服务运行正在编辑的开发文件。针对开发进程限制资源；压力测试单独控制规模，避免影响同机正式游戏和已有 Milvus。共享数据库实例和主机仍有共同故障、维护与资源边界，两个数据库并不等于两台机器的隔离。

正式访问继续使用 `https://game.aicoding.ltd/` 和 Caddy。开发测试默认可通过 SSH 将服务器 `127.0.0.1:3211` 转发到访问端；需要手机或其他玩家共同验收时，再配置独立 HTTPS 测试入口。直接使用 `117.72.116.83:测试端口` 访问网页也可行，但须实际设置监听、Caddy 路由和云安全组；IP 入口不能自动沿用域名的 HTTPS 证书。域名 HTTPS 入口更适合登录和跨设备测试，测试入口的具体地址在部署时确认并记录。

PostgreSQL 默认只接受本机连接；远程管理使用 SSH 隧道，无需公开数据库 5432 端口。数据库数据保存在服务器磁盘上并按环境备份。先在开发环境验证迁移与恢复，正式 SQLite 迁移沿用上文的暂停写入、校验和回滚流程。

开发目录与独立 service 已按此隔离建立，当前先使用独立 SQLite 数据目录 `/var/lib/pair-play-dev`。两个 PostgreSQL 数据库仍是待实施目标，不能视为已创建；正式仍运行 SQLite。实际环境及接手步骤见 [handover](handover.md)。

公共契约包只包含协议和可公开结构，不能把服务端完整引擎快照、密码处理、数据库连接或秘密规则依赖打进浏览器产物。服务器为每名玩家生成可见视图。

前端按游戏懒加载组件，游戏数量增加不要求每次进入大厅都下载所有游戏界面。通用配置及访客视图由各游戏声明。

## 对局型与长期型并行

注册表区分 `match/persistent`。下棋、打牌有房间、准备、回合和结算；农场、牧场有持续档案、时间结算、仓库和资源动作。两类共用认证、大厅、数据访问和主题。

作物保存种植与成熟时间，重新进入后按服务器时间计算。需要产出入账的结算与游标推进进入事务，不能仅依赖浏览器定时器。用户去下棋、关手机或后台重启后，农场仍按已保存的规则推进。

牌类游戏手牌、农场私人仓库等使用不同玩家视图；互访并不等于获得修改权限。长期存档不随房间关闭销毁。

## 性能与扩展依据

游戏数量主要增加代码与界面规模，实际容量取决于在线连接数、每秒操作次数、状态大小、事务耗时和计算负载。上线后按这些指标评估，不承诺未经压测的并发人数。

共享大厅事件与房间 / 档案事件分流，只发送必要变化。写入失败不能向客户端宣布成功；多房间操作不能误修改彼此状态。CPU 密集的棋类搜索或大型模拟放到独立计算任务，避免长时间占用 API 处理流程。

以后若运行多个 API 实例，再增加共享在线状态、房间归属和跨实例消息协调；PostgreSQL 可以是共享持久层，但不能把某个进程的内存房间误认为已经跨实例一致。

## 落地顺序

1. 先在新结构中建立 TypeScript 契约、Fastify 服务和游戏注册，将猜数字规则迁入独立模块，保留现有 API 的兼容入口。
2. 用 Vue 迁移大厅、房间、输入和复盘组件，保持日夜主题、手机键盘、草稿、邀请与断线体验。
3. 完成 PostgreSQL 迁移演练及校验，按统一部署版本切换；这一步在正式长期游戏启用前完成。
4. 建立长期档案服务和时间结算，再接入农场 / 牧场；棋牌按对局模块接入。

验收包含现有游戏回归、类型检查、API schema、旧数据迁移、隐私、多设备、重复动作和资源并发操作测试。设计完成不代表已执行这些迁移。
