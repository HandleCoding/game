# 一起牧场有限生产与名宠堂技术方案

实施状态（2026-10-05）：基础生命周期、名宠堂、昵称与归档记录已按本方案实现；实际冻结数值见ranch-balance.md，验收/发布见handover与20261005-ranch-lifecycle报告。下文数值草案不应替代最终配置。变异/前缀/符文尚未实现。

更新日期：2026-10-04。状态：设计稿，未实施、未迁移、未发布。本方案总结用户已确定的动物生命周期和“名宠堂”名称，并给出下一阶段的规则、数据、接口、数值验收和上线办法。逐物种时间和轮次为完整首轮调参草案；认养价格、产物收益和经验必须经过模拟再冻结，不能直接拿当前小时制价格配合新的分钟制周期上线。

## 设计结论与范围

动物循环：认养幼崽 → 成年 → 有限轮次生产 → 收完最后一批 → 进入名宠堂、出售或放生。名宠堂保留每只动物的身份、外观、名字和成长记录，未来的变异与前缀同样保留。动物不自动死亡、不自动出售、不因为离线消失。

已确定：初期采用5、10、30、60、120、180、240分钟梯度；后期衔接此前讨论的8、12、24小时。成长时间与每轮生产间隔分开；完成后由主人选择去向；全部注册玩家可参观，无好友申请机制。保留沉浸式场景、侧边食槽、柔和写实幼年/成年、手机和电脑共同进度。

工程建议：按实际生成轮次结束生产；缺粮和存量满时暂停有效进度；暂停不损失生产轮次。名宠堂不占生产栏位、不耗粮、不产金币或经验。首期不实现变异概率、前缀效果、符文玩法、繁殖、跨玩家交易、偷取或合作委托，只设计可扩展的数据边界。

## 已有代码与缺口

云端开发目录 /opt/pair-play-dev。核对时正式版为2.6.2、数据库schema v3。实际技术栈是Vue 3 / TypeScript / Vite、Node.js / Fastify / TypeScript、PostgreSQL，动作HTTP、变化提示SSE，Caddy主站HTTPS及现有公开图片CDN。保持模块化后端，不增加另一套Python服务。

现有引擎 apps/api/src/games/animal-ranch/engine.ts 保存每只动物购入周期；用ageMs推算无限生产，stored最多3轮，满存仍吃粮。storage.ts每次保存会删除并重插该档案的全部动物行；日志界面最近20条不能充当永久成长档案。ranch_inventory只按产物种类聚合；若沿用目录实时售价，会让已有产物随调价改变价值。

本方案需要新的有限轮次引擎、存量暂停结算、独立身份与归档、按来源保存的产物批次以及生命周期动作。不能只新增一个retired布尔值，也不能把名宠堂动物继续塞进生产animals数组。现有账号、猜数字和其他游戏规则不变。

## 动物状态与退出规则

永久存储的状态为 juvenile、producing、completed、hall、sold、released。饥饿、满存、可收获是计算得到的附加状态，可以同时存在，例如“可收获且缺粮”；不要用单一phase覆盖它们。

- juvenile：按有效喂养时间成长。
- producing：经过第一轮完整周期后生成首批；每成功生成一批completedRounds加1。首期保持当前“成年后再等一轮”的语义，界面同时显示成年倒计时与第一次产出预计时间，避免混淆老QQ牧场资料。
- completed：已生成全部有限轮次，立即停止吃粮和计时；仍有产物时先显示“最后一批可收获”，全部收完后显示“生产已完成，选择去向”。
- hall：完成全部生产且无未收产物后进入名宠堂；释放生产位置，可查看、改昵称、收藏展示。首期不允许返回生产、不重置轮次。以后仍可主动出售或放生，操作保留历史。
- sold：出售一次，按该实例服务端保存的退出规则获得金币；记录保留但不再显示为在场动物。
- released：放生，不获得出售金币；记录保留并标明已放生。

幼年及生产中的动物允许提前出售、放生；必须先清空已生成产物。提前进入名宠堂首期不开放，避免未完成生产的动物被误归档和“恢复生产”套利。名宠堂不是物种解锁图鉴：同一个物种的不同个体均能分别收藏。

出售与放生均在游戏内展示动物全名、去向、实际金币、不可重新认领的说明并让玩家确认。进入名宠堂展示“停止生产、保留个体、不占栏位”。名宠堂再出售/放生也有确认；不做批量永久删除功能。后台运维清空、删除真实进度仍须用户另行明确确认。

## 数值方法与上线门槛

所有金额、份数、经验、毫秒为校验后的整数；不能让前端决定价格和剩余轮次。保留逐级增长的等级经验公式作为第一轮基线：80 + 25×(L-1) + 10×(L-1)²；是否最终采用以完整生命周期模拟为准。

为每种动物联合配置认养价P、总轮次N、单轮产量Y、产物售价S、完整有效养殖期T、饲料成本F、总生涯经验X、退出返还函数E。关键测量为：

- 完成生涯且进入名宠堂/放生的净收益 = N×Y×S - P - F。
- 完成后出售净收益 = 上述净收益 + E。
- 单位置净收益/小时 = 完整生涯净收益 / T，必须计入幼年、换购和未及时收获，不能只算成年产能。
- 单位置经验/小时 = X / T。新手短周期不应因“收获次数多”获得额外无限奖励。
- 购买、出售动物、出售产物、放生、进入名宠堂、喂食、扩建给0经验；经验仅在真正收取生成批次时授予，且每批至多一次。

首轮经济目标建议：完整生产收益扣认养与食槽成本后仍为正；进入名宠堂也能回本。出售完成动物只是小额附加收益，不作为回本必要条件。短周期低阶的每小时经验与净收益应低于稳定阶段的正常组合，长周期有便利性但不允许同时在全部指标上压倒其他同等级选择。具体收益百分比、36种认养价/售价/经验暂未冻结，旧版价格不得直接照搬。

出售返还首轮建议基线：幼年floor(P×0.30)；成年随已生产比例从60%平滑降至15%，E=floor(P×(0.60-0.45×completedRounds/N))；完成后15%。gift来源实际支付额P为0，禁止系统赠送动物按商店认养价变现。退出公式按实例快照保存；“收产物后卖出”的任意阶段策略也必须模拟，若提前成年出售比完成生涯明显更赚钱就调整价格/返还，不能只检查完整生涯。

生涯经验按轮次分摊，第k轮XP = floor(kX/N)-floor((k-1)X/N)，累计恰好为X。批次保留自己的XP；不能通过反复点收获得到额外经验。如果X小于N导致部分轮次0XP，UI须明确显示或重调X，不用每轮强制+1破坏总预算。仓库出售不再给第二遍XP。

发布前必跑1、7、30、90天策略模拟：5分钟高频、1/4/8/12/24小时回访；低阶循环、高阶循环、混合动物、各时点提前出售、只进名宠堂、只放生、缺粮与满存。至少应满足：

1. 连续高频游玩一下午不能解锁全部36种；建议首日落在Lv3–5，最终日期仍由用户体验调参决定。
2. 正常完整养殖并全部进入名宠堂不会因动物循环本身持续亏本。
3. 买入后立即出售/放生、重复退出、两设备收同一批不能创造资源。
4. 24小时回访玩家不会因存量溢出丢轮次；实际进度可暂停，不能承诺与高频完全等收益。
5. 与稳定等级匹配的组合比反复刷初级动物有合理收益优势；不能只比较购买价格。
6. 初始食槽在4只活跃动物下至少覆盖24小时；目前240份基线理论30小时，动态暂停只能降低实际消耗。

实施者须输出36种完整配置及模拟报告。时间/轮次草案通过模拟和实际体验后才算可发布数值。

## 名字与未来变异结构

每只动物有不可复用的UUID，与物种ID、主人ID分开。老animal-1仅作为旧档案内局部ID，不能用于跨档案收藏或未来交易身份。展示数据保持分层：

- speciesId：例如rabbit，决定物种与基础模型。
- nickname：主人昵称，可为空；不修改系统词条。
- variantId：外观变体，首期normal；未来可以是雪白、金色等独立资产映射。
- rarityId：品质，首期common；首期不因稀有度提高收益。
- affixes：前缀/后缀条目列表，首期空；每条包含definitionId、definitionVersion、实际roll值、生成事件ID。
- runeSlots：预留关联设计，不把未来符文效果写进昵称，首期不开放装备动作。
- appearanceVersion、rulesVersion、rulesSnapshot：确定可追溯的外观与有效经济参数。

示例未来展示：“月辉·垂耳兔”，下面另行显示昵称“团团”；系统前缀与昵称视觉区分，搜索可按物种、前缀、品质、昵称筛选。示例名字只是表现方向，不代表变异系统已上线。

词条定义和经济计算由后端拥有，前端仅接收可公开名称、描述、视觉ID和服务端计算结果。以后增加变异，在认养或指定成长节点进行一次服务器随机并写入同一事务；以animalId+事件类型+事件序号唯一约束防止刷新、重试、换设备重抽。纯引擎通过上下文注入随机，测试用固定序列；禁止客户端决定随机结果或在展示计算中重新抽。

建议先只加视觉/收藏词条，再讨论产量、间隔、耗粮词条。经济词条采用固定白名单、明确叠加顺序和上下限；规则升级或换符文只作用于之后的完整周期，已生成批次不可重算。初期总轮次在认养时锁定；任何词条不能刷新已完成轮次、让名宠堂动物恢复生产。后续繁殖、符文拆卸、交易需独立设计，并与既有实例身份和批次账本衔接。

资产使用variantId→明确素材映射，缺变体素材回退该物种正常幼年/成年；不能用未适配动物的重复贴图冒充36种变异。保持已有clipPath帧边界、脚底对齐、自然阴影、解码缓存、进度和CDN回源。

## 离线结算算法

只按服务器时间和上次结算游标推进，不需要后台每秒写库或启动world_jobs worker。总生涯不是现实时间到期删除：缺粮、满存会拉长现实持续时间。

按事件边界推进共享食槽，活跃集合为幼年及仍可产出且未满存动物。下一事件是某只成年、某只本轮完成、食槽耗尽或now：

1. 得到当前活跃数A及每只耗粮速率，求该区间可共同喂养的时长。
2. 推进至最早事件：扣一次食槽，增加相应成长/轮内有效时间。
3. 成年转producing；轮内时间满时生成唯一批次并增加completedRounds。最后一轮生成即转completed；达到存量上限从活跃集合移除。
4. 重新计算剩余活跃集合和食槽速率，处理同一毫秒全部边界；直到now或无可推进动物。
5. 缺粮时保存当前剩余进度；补粮动作结算旧时间后再添粮，之后从当前时间恢复。满存期间不积攒隐藏周期。

全部使用整数或持久化余数，避免“离线一次”和“每分钟结算”因舍入得到不同数量。算法复杂度以本次有限生产事件数为界，避免按离线秒数循环。旧无限生产实例走显式legacy适配；不得把一只老动物离线几年时遍历上百万周期。

生产generated_at按事件发生时刻记录，不能全部记成打开页面的时间；但缺粮/满存暂停后到期必须重新计算，不按最初nextAt强行发货。客户端展示服务器算出的remainingMs/nextAt与暂停原因，倒计时到0请求刷新而非发资源。

## 动作接口与一致性

复用POST /api/games/animal-ranch/actions，现有会话、requestId、expectedRevision。同档案SELECT FOR UPDATE事务内先结算，再验证动作、改变动物/批次/钱包/仓库/日记、写回执、递增revision，提交后发送SSE。随机、写库与变异事件将来也在该事务内完成；事务中不等待CDN或其他外部网络。

建议新动作：

- renameAnimal {animalId,nickname}，按长度/控制字符校验，展示经Vue转义；保留系统词条。
- enterHall {animalId}，要求completed且没有未收批次。
- sellAnimal {animalId}，复用名称但替换为新版本退出规则；仅允许本人有效状态。
- releaseAnimal {animalId}，不发金币且不删除纪念数据。
- setHallDisplay {animalIds}，上限6、去重、归属及hall状态校验。
- harvest {animalId?}，继续支持一键收；领取批次、转库存和XP同事务完成。

GET名宠堂及永久记录增加独立分页读接口，例如/api/games/animal-ranch/me/hall与/me/animals/:id/events；这些是待实现的新路由。访客访问明确的owner公开展示接口，默认只看主人选择的名宠堂展示，其他所有注册玩家可访问，无新增好友关系。

同requestId重复调用返回原结果；同requestId不同动作返回409。不同requestId并发出售/放生/进入名宠堂，行锁及状态检查确保至多一个终态转换成功。从hall继续出售/放生是新的、可追溯动作，hall进入奖励为0，因此不会重复发钱。旧revision返回409并刷新，不自动重放不可逆退出动作；昵称输入草稿仍保留。

时间结算若产生批次或生命周期改变，也应增加档案revision，并据提交结果通知；不能让GET修改生产状态却长期保持同一revision。查询名宠堂历史不触发全场无意义写入。读结算和动作共用逻辑，严禁两套实现。

## 前端界面与双端体验

保持铺满屏幕的游戏场景，名宠堂从工具菜单进入独立木质窗口/场景子页。动物点选详情显示头像、系统名、昵称、成长/生产状态、“已生产3/6轮”、可收产物、下一轮时间和预计饲料支持；完成后显示三个去向按钮。产物未清空时先提供“收取最后产物”，退出按钮解释原因。

生产动物头顶状态依次展示可收获、生产已完成、缺粮、存量已满；优先显示可操作项，并能在详情看全状态。提示不再浮放底部遮挡animal-picker，保留左上资料牌提示和侧边食槽标识。退出动画只在服务器成功提交后播放；低动态设置简化动画。

名宠堂包含个体卡片、物种/品质/前缀筛选、昵称、来源、生产完成时间、总轮次与累计产量、成长日记、展示选择。图鉴继续按物种汇总，但分开“等级解锁”“真正养过”“完成生产”“进入名宠堂”。重复物种不覆盖独立个体；出售/放生记录在成长档案查看，不占名宠堂在堂列表。

手机竖屏使用全宽面板、独立内容滚动和固定操作区；横屏和电脑采用列表+详情。确认按钮、关闭按钮≥44px，滚动不点击穿透Canvas，安全区和软键盘不遮动作。每次轮询不重建全部页面，保留搜索、草稿、选择和滚动。名宠堂只加载可见卡片所需图集，复用现有真实加载进度与回源，不预载所有未来变异。

## 旧数据迁移与发布

本方案不授权清空正式数据，也不修改线上账号或动物。后续实现默认保留迁移；若用户另要求重置，必须再次确认范围并备份，不能沿用此前一次性重置许可。

- 先新增可兼容字段/表，保留旧数据；迁移状态版本和动物规则版本分别管理，不能把改目录当成存档迁移。
- 旧animal-1等映射为新UUID，用(gameId,worldId,owner,legacyId)唯一关联，映射可幂等重跑。
- 旧实例保留购入时growthMs/cycleMs/yield/harvestXp/paid和已有ageMs/stored。旧版没有历史生产总量，不能从ageMs推断为准确已收轮次，因为满存也继续计时且旧收获可能合并。
- 首轮建议旧存量成为legacy待收批次，保留原XP与数量；已有动物从切换点获得物种的新有限剩余轮次，progress保留当前轮内比例但不追补历史丢弃的产物。明确标注“旧版迁移”，不得伪造原来的出生、成年、累计产量和变异。
- legacy存量不占新轮次，不因超出新存量上限丢弃；未收前允许暂停新生产。原赠送动物缺准确支付来源时，不追溯宣称paid为0，标legacy并保留原退出规则，后续新赠送才准确记gift。
- 旧库存按切换时旧目录售价生成legacy inventory lot；保留数量与权益，之后新价格仅作用于新批次。金币、XP、食槽、容量和已解锁进度保持；高等级不会自动降级，新规则只控制以后增量。
- 开发隔离schema演练真实格式的匿名夹具；正式上线短暂停写，旧规则结算到切换点、备份、迁移、验证后启用新规则。行锁迁移和维护锁保证不会在旧/新引擎同时写同一档案。
- 校验账号/会话/猜数字数量不变，牧场金币/XP/饲料/库存/原动物映射不丢失；旧累计统计标unknown并从切换点累计，不能填0冒充真实总历史。
- 数据库、PersistentDefinition.metadata.version、state.version、load/save契约和前端视图版本一起验收。现persistent.ts直接拒绝版本不一致，需加显式迁移适配或维护批量完成，不可只把metadata.version改为2。
- 新版本开始写批次/名宠堂后不能直接回滚到会删除并重插动物的旧storage。回退只能使用兼容新schema的新规则禁用版本，或停写后经审查恢复；不得用旧备份覆盖上线后用户新进度。

部署仍按deployment-runbook。只发布经过验收的代码和新增迁移，不重启/修改Milvus等无关服务；Git推送不等于正式部署。
